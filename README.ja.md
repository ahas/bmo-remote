# bmo-remote

コンソールのリモートアクセスを、独自の API を持つ一つのサービスとして提供します。サービスが動くマシン上の
ターミナルセッションは専用の tmux サーバーが保持し、そのマシンのデスクトップには GNOME のリモートログイン経由で
RDP 接続します。ブラウザーの IronRDP クライアントはリレーに RDCleanPath で接続します。サービス独自のコマンド
`bmo-remote node
remote-desktop` は、リレーが接続するポートを表示・設定します。このサービスは他のユニットを呼び出さず、前段の
コンソールがリモート画面のリクエストを中継します。詳しくは `docs/api.md` を参照してください。

## テスト

テストベッドの `personal-data` チェックは、追跡対象のすべてのファイルからメールアドレス、ホームパス、電話番号、
トークン、プライベートネットワークアドレスを探します(`PERSONAL-DATA.md`)。`tests/` のテストは一つのテスト
ターゲット `tests/main.rs` にまとめられ、各テストファイルはそのモジュールです。内訳は次のとおりです。旧アーカイブに
残されたデスクトップのポートをストアに取り込む `tests/import.rs`、ターミナルセッションに貼り付けた画像がセッション
専用のファイルとして保存され、セッションとともに消えることを確かめる `tests/pastes.rs`、そしてコンソールフェイスを
扱う `tests/console.rs` です。`tests/console.rs` は、サービスが提供するマニフェストを、クライアントが vendoring
したリリース上で bmo-ui 自身の読み方で読めること、サービスの宣言と資格情報が bmo-chat のコンソールフェイスに
接続されること、画面が必要とする箇所でコンソールの資格情報と閲覧者のロールを求めること、サービス自身のトークンが
フェイスでは拒否され画面のルートでは受け付けられることを確かめます。フェイス自体のルールはそのクレートのテストが
担います。テストは `cargo test` で実行し、マニフェストの読み取りは vendoring されたリリースファイルに対して bun で
実行します。
ファイルを書くテストはシステムの一時フォルダー配下の専用フォルダーに書き、tmux サーバーを起動するテストは専用の
ソケットで起動します。どちらもテストが成功してもパニックしても、テスト終了時に片付けられます。
バンドル自身のテストは `client/tests/` にあります。応答しないデスクトップに対し、応答する、拒否する、または手放される
まで再試行することを、代役のデスクトップと代役の時計で確かめるテスト(`docs/remote.md`、「A
desktop that does not answer」)のほか、画面のセッション一覧、表示操作、ターミナルへの貼り付けのテストを含み、
バンドルのチェックの一部として `client/` 内で `bun run test` により実行します。その他の振る舞いテストは保留中です。
最小限のサービスが新しいリポジトリ上で動くようになった時点でここに書いて実行し、それまではすべてのターゲットを
コンパイルしてクレートをフォーマット・リントするテストベッド自身の静的チェックと、バンドルおよびデスクトップ
サイドカーのチェックがその代わりを務めます。
`docs/inventory.md` には、旧来の振る舞いを検証していたテストの一覧があります。

## 構成

| フォルダー | 内容 |
|---|---|
| `src/` | サービスとそのコマンド。一つのクレートを独自のモジュールに分割したもの |
| `migrations/` | ストア。テーブルを順に作成する文 |
| `client/` | コンソールプラグインバンドル。リモート画面を収めた独立したプロジェクト |
| `desktop-sidecar/` | デスクトップサイドカー。デスクトップのソケットに応答するためにサービスが起動する bun パッケージで、独立したプロジェクト |
| `deploy/` | サービスのユーザーユニットと、セッションの tmux サーバーが使う tmux 設定 |
| `tests/` | 現在維持されている振る舞いテスト |
| `docs/` | サービスの動作を定める正式なドキュメント |

ルートには Cargo マニフェストとそのロックファイル、MIT の `LICENSE`、`VERSION`、`testbed.toml`、`install.toml`、`rustfmt.toml`、
`CLAUDE.md`、`PERSONAL-DATA.md`、`korean-ledger.json`、`settings.toml`、そしてデプロイ側が用意するローカル設定の
例である `settings.local.toml.example` があります。

## コンソールプラグインバンドル

`client/` は、コンソールのリモート画面を bmo-ui のコンソールプラグイン規約に沿ったバンドルとして収めています。
IronRDP Web クライアントの RDP バックエンドは `client/vendor/` に、それをビルドするスクリプトは `client/scripts/`
に vendoring されており、`docs/openapi.json` から生成した TypeScript クライアントを `client/shared/openapi.ts` に
含みます。バンドルは bmo-chat の `shared-versions.toml` が固定する bmo-ui のリリースを土台とし、そのリリースは
`client/vendor/` に vendoring されています。`bun run bundle` は bmo-ui のバンドルビルドでページを `client/dist/`
にビルドし、コンソールが提供しないものは `client/module/` から補います。サービスは bmo-chat のコンソールフェイスを
通じてバンドルを提供し、デプロイ時にリリースの中でビルドされます(`docs/api.md`、「The console face」、「The console plugin bundle」)。

画面は拒否をそのコードに応じてパックの文言で表示します。バンドルのチェックは `client/` 内で実行する
`bun run check` で、ロックされたパッケージをインストールし、型チェックを行い、テストを実行してからモジュールを
ビルドします。テストベッドはこれを独立したプロジェクトのチェックとして実行します。

## ドキュメント

| ドキュメント | 内容 |
|---|---|
| `docs/remote.md` | ターミナルセッションとデスクトップ:何がそれを保持するか、何がやり取りされるか、そして境界 |
| `docs/screen.md` | コンソールのリモート画面:タブ、ビュー、メニュー |
| `docs/api.md` | ルート、ソケット、そのメッセージと拒否、コマンド、ストア、設定、コンソールフェイス、コンソールプラグインバンドル、そしてコンソールが行うこと |
| `docs/inventory.md` | このリポジトリが旧リポジトリから引き継いだものと、各まとまりの件数および出典 |
| `PERSONAL-DATA.md` | このリポジトリに決して置いてはならないもの(個人の名前、住所、パス、デバイスやネットワークの情報、ルームのメンバーや会社の情報、実際の会話の一行)と、それを守るチェック |

## バージョン

`VERSION` はリポジトリのバージョンを保持し、クレートとコンソールプラグインバンドルがこれを共有します。最初の
リリースまでは `0.1.0` にリビジョン接尾辞を付けた形で、規則は `docs/api.md` の「Versions」に記載されています。
